# Partner iOS P1 local remediation

Baseline: 9f7569b4df85fc80279fbb4726c8531ce18794f1. Dedicated branch: codex/partner-ios-p1. No Production deployment/record or storage inspection, Apple registration, native build, TestFlight, OTA, or Customer/Captain application edit occurred.

## Implemented boundaries

- Drafts: a first-party business-field allowlist is applied before client transmission, on backend writes (including application-derived drafts), and on legacy reads. Unknown credential/session keys and nested/wrongly typed data are rejected by the backend. OTP/password inputs remain transient; the short-lived verification proof is never serialized into a business draft. Historical cleanup is a separate unexecuted plan.
- Applicant handoff: verified pending applicants receive a 15-minute access JWT with explicit karigo-partner-onboarding audience/scope and a hashed, rotating seven-day restricted refresh session. The normal JWT strategy rejects that scope, even after approval. Own draft/status/documents/deletion only; approved operational access requires fresh normal sign-in. Refresh/logout serialize per account; revoked sessions fail closed. Password setup needs a fresh one-use OTP-derived proof. The legacy proofless password endpoint is closed. Legacy application submission/status endpoints also require authenticated ownership; integrate any outside callers with that reviewed handoff before a later deployment.
- Session storage: the versioned Partner session/legacy migration store explicitly uses SecureStore WHEN_UNLOCKED. No Captain AFTER_FIRST_UNLOCK policy, biometric prompt, AsyncStorage secrets or locked-device work is introduced.
- Deletion: business-role closure remains distinct from permanent whole-account erasure. Pending and approved users can initiate the latter in-app without contacting Support. Consent includes every genuine KariGO role; the server also checks the confirming account ID. A private, non-restoring receipt is saved in SecureStore before transmission and survives a lost response/sign-out. Access/credentials/sessions/devices are disabled immediately; active assignment evidence is preserved for reconciliation rather than discarded. Ordinary data is erased/minimized after work, financial and legal blockers are resolved. Reviewed completion is an explicit restricted admin operation, not an automatic financial mutation. UI explains the 30-day post-blocker timing, necessary legal/financial retention and 90-day post-completion receipt window.
- Erasure completion reuses the reviewed Customer/Captain minimization adapters under a separately consented Partner whole-account request; their existing public paths are unchanged. Partner profile/contact/catalogue/draft/file/payout data is minimized, all sessions/devices removed, and paid amounts/references retained. Active holds or storage failures block completion. Legacy unlinked provider identities require verified review rather than guessing ownership from a matching phone/email. The external-cleanup evidence reference must cover legacy/public catalogue files, processor copies, approved retention/hold review, and backup/deletion-journal handling. Never attest completion while a required external cleanup or independent restore-suppression record is outstanding. The existing retention policy remains authoritative; no ad-hoc financial expiry is invented.
- Private uploads: owner-scoped pending/approved access, opaque HMAC/random object keys, stored provider/bucket provenance, MIME/magic/actual-size limits, controlled admin document review and private/no-store/nosniff reads. Approved evidence needs reviewed erasure; unapproved files can be removed. Withdrawn application cleanup removes linked file bytes/draft content subject to retention review; failures are retryable through the restricted cleanup endpoint. Modern system pickers select files/images without broad library permission or camera capture. Only picker-created local cache copies are removed after upload. Multipart requests have a 30-second deadline and a single auth-refresh retry on 401, not blind network retries.
- Merchant push: SDK53-compatible expo-notifications, default-off preferences, contextual permission, foreground display, approved/owned tap routing and token refresh/re-registration. PARTNER_APP registrations cannot reuse Customer/Captain registrations; generic registration cannot repurpose Partner tokens. Logout/full deletion removes Partner registrations. Expo transport is selected specifically for Partner without changing the global Customer/Captain transport. General lock-screen text contains no customer, address, bank or amount details. Existing paid-order/status/cancellation and paid-settlement flows are used; no support/message flow is invented. A transactional paid-order outbox survives payment rollback boundaries; bounded claims/retries recheck approval/ownership/preferences. Delivery outbox records expire after seven days. As with any push network, an uncertain provider acceptance may lead to duplicate delivery; taps re-authorize and are deduplicated locally. Real APNs delivery remains a later physical/native gate.
- Financial review: payout writes remain Partner-scoped, sensitive-action restrictions and masked readback stay in force, and ordinary profile responses omit full bank details. Persistence errors are translated before global error-stack logging can expose input bank values. Bank data stays in memory during editing, not unencrypted local storage. Restricted backend bank storage and hosting encryption/access configuration must be verified when deployment is separately authorized; P1 did not inspect Production configuration. Payment provider design is unchanged.

## Configuration and release gates

Production API target is unchanged. No verified Partner staging API was established. Staging/simulator profiles have no hard-coded Production URL and require explicit PARTNER_STAGING_API_BASE_URL. Build-time and runtime checks refuse missing targets, known Production staging hosts, non-HTTPS and credential-bearing URLs. Synthetic .invalid URLs in configuration tests are not deployed staging services.

Intended iOS IDs: ng.com.karigo.partner and ng.com.karigo.partner.staging; neither was registered. Android IDs/version codes are unchanged. iOS supportsTablet=false resolves to device family [1]. Camera, microphone, location, contacts, Bluetooth and background-location descriptions/modes are absent; broad photo-library permission is disabled. Notifications do not enable background remote-notification mode. Generated development APNs entitlement is configuration evidence, not a signed Production entitlement assertion.

Future iOS build profiles pin macos-sequoia-15.6-xcode-26.2. Expo documents opting SDK53 into that image: https://expo.dev/blog/app-store-connect-minimum-sdk-26 and https://docs.expo.dev/build-reference/infrastructure/. No Xcode/native compilation was attempted.

The local SQL migration creates only Partner scoped-session/file/push tables and adds PARTNER_APP. It was rehearsed against a separate loopback baseline database and must not be applied to Production without a later reviewed deployment.

P2 may proceed as local operational UI work using the exact existing contracts in p2-order-actions.md. Native simulator execution is not verified and is not ready against a verified staging service until one is supplied. Physical permission/picker/push/deletion smoke, signed-artifact/privacy-manifest inspection, storage/processor deployment verification and Apple actions remain later gates. Partner submission remains paused while Customer/Captain appeals are unresolved.
