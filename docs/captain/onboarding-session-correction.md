## Authentication and lifetime

Normal `POST /api/v1/auth/login` accepts a phone-verified RIDER with a completed
onboarding password and PENDING account status. It issues a JWT whose subject is
the stored user UUID and whose scope is `captain-onboarding` (15-minute lifetime).
It does not activate or approve the account. The refresh secret expires after one
day, is stored only as a hash, rotates through the existing refresh mechanism,
and retains an integrity-protected `co1.` prefix to distinguish restricted sessions
without a database migration. Modifying the prefix invalidates token lookup.

Every scoped request rechecks the stored role, verification, password setup,
account status, deletion requests, latest application decisions and disabled
Captain profiles. Rejected/trashed applications and suspended/deactivated/deleted
identities fail closed. Client roles and status claims cannot grant access.

After approval makes the account ACTIVE, existing scoped JWTs remain restricted.
Refresh or a new normal login can issue ordinary access; operational approval
checks still apply. Existing Customer/Vendor/Admin sessions retain their behavior.
The general OTP endpoint cannot activate a pending Captain: the dedicated Captain
OTP endpoint must be used.

## Endpoint allowlist

All paths have the `/api/v1` prefix. The common JWT guard denies scoped sessions
by default, with method-only opt-in on the following handlers:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/auth/me` | Identity/session restoration |
| POST | `/auth/logout` | Revoke owned refresh session |
| GET | `/captain/access` | Onboarding status and next step |
| POST | `/captain/application-documents/uploads` | Private owned upload |
| GET | `/captain/application-documents` | Owned document status, no storage paths/admin notes |
| DELETE | `/captain/application-documents/:documentId` | Remove owned unsubmitted upload |
| POST | `/delivery-captain-applications/me` | Submit personal/application fields and documents |
| GET | `/delivery-captain-applications/me` | Owned application status |
| POST | `/delivery-captain-applications/me/revision` | Requested application revision |
| POST | `/taxi/driver-applications/me` | Submit licence/vehicle/application fields |
| GET | `/taxi/driver-applications/me` | Owned Ride Captain application status |

`POST /auth/refresh` validates the hashed refresh secret and current server-side
eligibility independently; it is not a bearer-token permission. Existing public
reference/catalogue endpoints retain their public access.

No operational endpoint is opted in: online/availability, dispatch/offers,
acceptance, work state, location reporting, earnings/remittance, payments and push
device registration remain denied. Ride realtime rejects scoped JWTs even after
approval. Existing background-location code confirms accepted work through the
server before persisting/sending samples and stops when that check is denied.

## Release boundary

This change is backend-only. Existing Captain sign-in/session restore and access
resolver can use the restricted session. It does not auto-sign-in from password
setup: after setting a password, the applicant signs in through the normal login.
Physical onboarding acceptance is required after a separately approved deployment.
No QA account, Ride, Delivery, wallet funding, provider call, OTP or email is
generated by the local tests; provider/storage dependencies are mocked.
